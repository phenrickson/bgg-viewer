## Goal & success criteria

A `/whats-new` page in bgg-viewer showing every game added to the warehouse in the
last 7/30/365 days, each linking straight to its detail page, with a badge on
standout `predicted_hurdle_prob` rows. Done when the page is live behind the
existing login, the list is never filtered by the badge logic, and both repos'
verify commands pass. Two repos, two PRs, sequenced — the warehouse-api endpoint has
to exist and be deployed before the viewer page can show real data.

## Why two repos

bgg-viewer never queries BigQuery directly for this feature — it goes through
`warehouseClient()`, same as the game-detail page. `src/warehouse/readers/games.py`
already has `get_provenance()` reading `raw.fetched_responses`, and warehouse-api's
runtime SA (`bgg-data-warehouse@...`) already has full BigQuery access — so unlike
the earlier draft of this plan, **there is no IAM/Terraform prerequisite at all**.
The only new access this feature needs already exists.

## Steps

### Part A — bgg-data-warehouse

#### 1. Reader

`src/warehouse/readers/monitoring.py`:

```python
"""Reader for the 'what's new' monitoring view — games recently added to the warehouse."""

from typing import Any, Optional

from google.cloud import bigquery

from src.warehouse.bq import dataset, get_client


def fetch_recently_added(
    days_back: int = 7,
    limit: int = 200,
    client: Optional[bigquery.Client] = None,
) -> list[dict[str, Any]]:
    """Games first fetched in the last `days_back` days, newest first.

    `first_seen` = MIN(fetch_timestamp) per game_id from raw.fetched_responses —
    same definition bgg-dash-viewer's /app/new-games page already uses.
    predicted_hurdle_prob is returned raw/unthresholded; tiering is a display
    decision made by the caller.
    """
    client = client or get_client()
    sql = f"""
        WITH first_fetches AS (
            SELECT game_id, MIN(fetch_timestamp) AS first_seen
            FROM `{dataset('raw')}.fetched_responses`
            WHERE fetch_status = 'success'
            GROUP BY game_id
        )
        SELECT g.game_id, g.name, g.year_published, g.thumbnail,
               ff.first_seen, p.predicted_hurdle_prob
        FROM first_fetches ff
        JOIN `{dataset('analytics')}.games_features` g USING (game_id)
        LEFT JOIN `{dataset('predictions')}.bgg_predictions` p USING (game_id)
        WHERE ff.first_seen > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL @days_back DAY)
        ORDER BY ff.first_seen DESC
        LIMIT @limit
    """
    job_config = bigquery.QueryJobConfig(query_parameters=[
        bigquery.ScalarQueryParameter("days_back", "INT64", days_back),
        bigquery.ScalarQueryParameter("limit", "INT64", limit),
    ])
    return [dict(row) for row in client.query(sql, job_config=job_config).result()]
```

**Verify:** `uv run --extra test python -m pytest tests/test_monitoring_reader.py` — a `RoutingClient` fake (same as `test_games_reader.py`) returning canned rows, asserting the query is called with `days_back`/`limit` bound as parameters, not interpolated.

async getNewGames(days: 7 | 30 | 365): Promise<NewGameRow[]> {
	const res = await authedGet(`/new-games?days=${days}`);
	if (!res.ok) {
		throw new WarehouseError(res.status, `warehouse GET /new-games failed (${res.status})`);

}

#### 5. Tier logic

`src/lib/monitoring/hurdleTier.ts`:

```ts
export type HurdleTier = 'standout' | 'promising' | null;

export function hurdleTier(prob: number | null): HurdleTier {
	if (prob == null) return null;
	if (prob >= 0.7) return 'standout';
	if (prob >= 0.5) return 'promising';
	return null;
}
```

**Verify:** `hurdleTier.test.ts` — boundary cases at exactly 0.5 and 0.7, `null` in, `null` out, 0.49 → `null`.

#### 6. Route

`src/routes/(app)/whats-new/+page.server.ts`:

```ts
import { warehouseClient } from '$lib/server/warehouse';
import type { PageServerLoad } from './$types';

const ALLOWED_DAYS = [7, 30, 365] as const;

export const load: PageServerLoad = async ({ url }) => {
	const requested = Number(url.searchParams.get('days'));
	const days = ALLOWED_DAYS.includes(requested as any) ? (requested as 7 | 30 | 365) : 7;
	return { games: await warehouseClient().getNewGames(days), days };
};
```

## Risks / unknowns / rollback

- **Sequencing**: Part B can be coded before Part A merges (it's all injectable/mockable), but `just dev` won't show real rows until the warehouse-api endpoint is deployed.
- **Query cost**: checked live — `raw.fetched_responses` is 458,252 rows / ~29 MB, growing ~1,030 rows/day; the actual query dry-runs at ~36 MB scanned. Cheap now and at 10x this size. No caching needed at this scale; revisit only if that changes.
- **Rollback**: bgg-viewer's four new files are additive — reverting that PR fully removes the page. The warehouse-api endpoint is additive too (new router, no existing route touched) — reverting that PR removes it with no knock-on effect, since nothing else calls it yet.
