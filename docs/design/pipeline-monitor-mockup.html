Where each section's data comes from

  • Verdict and today's chain: GitHub Actions run history across the three repos, grouped into one chain per day. Comes from a new /monitoring/pipeline endpoint on the warehouse API, so the viewer never holds a GitHub token.
  • The amber "green but no hand-off" state: a run that succeeded but whose next stage never started within its expected window. This is the signal neither GitHub nor the heartbeat raises today.
  • Data freshness and coverage: a new Dataform view, monitoring.pipeline_status, with one row per table: max timestamp, distinct games, and a count of the universe that table should cover. The viewer artifacts row comes from the artifact pointer's builtAt, which the viewer already reads.
  • Models: monitoring.deployed_models, rebuilt as a table on the serving tables: every version still behind a current prediction, so an older version still serving games shows up.
  • Services: the API calls each Cloud Run service's /health. This is the least valuable section and the first to cut.

Open questions for the spec

  • What does each table should cover? For example, do predictions cover every active game or only unrated and upcoming ones? This sets the coverage denominator, and a wrong denominator gives a permanently amber bar.
  • Fix vs. observe: should the spec also close the gaps it detects (make Dataform fail on a non-SUCCEEDED run, chain collection scoring off embeddings_complete), or only make them visible?
  • Push vs. pull: is the page enough, or should a red verdict also notify you (heartbeat-style failing workflow, email)?
